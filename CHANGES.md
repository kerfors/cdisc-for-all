# Changes

## Step 1 — the contract and the NSV Registry base graph (2026-11-26)

**Code.** The base mapping rule is stated as W3C CSV on the Web (CSVW) metadata: one table description per source table, generated from the source's LinkML module, which stays the one hand-kept description. `cfa` holds the shared helper: the pin check against Reference_Versions.json; text readers (xlsx with the OOXML escape `_xHHHH_` decoded, CSV per RFC 4180, TSV without quote handling); the IRIs; the generator of CSVW descriptions; our implementation of CSVW minimal-mode conversion for the subset used (an empty key component gives an empty path segment, an empty cell gives no triple, a quoted empty value and a missing value are the same); the longturtle writer; the graph hash (SHA-256 of canonical N-Triples); the Excel view writer (every cell text); the text hash (SHA-256 of the table as a JSON array, rows sorted by key); the Schema sheet; Provenance.json. Structural SHACL is generated by LinkML gen-shacl. `checks/00_Schema` checks the modules against the rule, generates the CSVW descriptions and the SHACL shapes, and tests the tools on fixtures. `checks/CSVW_Crosscheck` converts each base table with rdf-tabular, the reference CSVW implementation, and requires the same graph. `requirements.txt` lists the Python packages at the versions the builds were run with.

**Content.** The first base graph: the NSV Registry sheet "Approved NSVs-alpha", as published, with its Excel view and Provenance. The view rebuilt from the graph has the text hash of the source table: the graph is lossless.

## Step 2 — the COSMoS base graph (2026-11-26)

**Code.** The COSMoS LinkML module: one class per export CSV, named by its file name without extension as published, one attribute per published column, keys as published (bc_id + dec_id; bc_id; domain + vlm_group_id + sdtm_variable). Its CSVW table group and structural SHACL are generated by `checks/00_Schema`. `cfa.pins` finds the file of a CSV table by its file name and reads a pinned file by its name in downloads/ (a pin may carry the publisher's path, such as `export/`). The COSMoS reader notebook; the CSVW cross-check converts the published COSMoS files themselves with rdf-tabular.

**Content.** The COSMoS base graph: the three tables of the public export, Package 19, as published, in one graph; one Excel view per table (data sheet `Table`, since the table names are longer than Excel allows for a sheet name); Provenance. Each view rebuilt from the graph has the text hash of its source table.

## Step 3 — the SDTMIG and SDTM Model base graphs (2026-11-26)

**Code.** LinkML modules for the SDTMIG v3.4 and SDTM v2.0 variable tables: one class per table, named by the file name without version and extension (`SDTMIG`, `SDTM`), one attribute per published column. The tables publish no key; the row key is the smallest column set that identifies every row (SDTMIG: Dataset Name + Variable Name; SDTM: Class + Dataset Name + Variable Name, with Dataset Name empty for class-level variables). Generated CSVW descriptions and SHACL. One reader notebook per CSV source, from one template. The CSVW cross-check covers every CSV source. The CSVW check confirms that a quoted empty value and an unquoted empty value both give no triple, also in rdf-tabular.

**Content.** None published: the SDTMIG and SDTM Model graphs, views and Provenance are sign-in content, built locally (`.gitignore`).

## Step 4 — the SDTM CT base graph, scoped (2026-11-26)

**Code.** The SDTM CT LinkML module: the table of `SDTM Terminology.txt`, one attribute per published column, row key Codelist Code + Code (a codelist row has no Codelist Code, so its node has an empty path segment). The CSVW dialect is tab-separated without quote handling (`quoteChar: null`), given as the class annotation `dialect`. The scope, as the class annotation `scope`: the codelists COSMoS refers to or SDTMIG v3.4 binds, read from the COSMoS and SDTMIG base graphs, with the codelist row and every term row of each. Codelists that are referred to but have no codelist row in the file are listed in Provenance. The reader notebook. The CSVW cross-check compares the rdf-tabular graph of the whole file on the scoped graph's nodes; rdf-tabular does not honour `quoteChar: null`, so the check uses a quote character that does not occur in the file.

**Content.** The SDTM CT base graph for the codelists in scope, its Excel view and Provenance. The view rebuilt from the graph has the text hash of the source rows in scope.

## Step 5 — the NCIt FLAT and NCIt code–CUI map base graphs, scoped (2026-11-27)

**Code.** LinkML modules for the NCIt FLAT file (`Thesaurus.txt` in the pinned release zip) and the NCIt code–CUI map. Neither file has a header row: the FLAT column names are the nine the NCI EVS ReadMe of the pinned release gives; the map's first two fields are `code` and `CUI` as the same ReadMe gives them ("code <pipe> CUI <pipe>"), and the further fields, which the ReadMe does not describe, are named by position. FLAT rows keep NCI's concept IRI as their node (a CSVW `aboutUrl` template on the code), checked against the published `concept IRI` cell. The scopes, as class annotations: for NCIt, the concepts of the SDTM CT rows in scope, the COSMoS BC and DEC concepts and the SDTM v2.0 Model variable C-codes, with all their ancestors; for the map, the codes of the NCIt graph. `cfa.read` reads delimited text without a header; `cfa.pins` reads a file pinned inside a zip, with both pins checked; `cfa.rule` takes an `aboutUrl` from a class annotation. Reader notebooks for both. The CSVW cross-check converts the published lines of the codes in scope.

**Content.** The NCIt FLAT base graph and the code–CUI map base graph for their scopes, their Excel views and Provenance. Each view rebuilt from its graph has the text hash of the source rows in scope.

## Step 6 — the linked layer: published-key links and Link_Check (2026-11-27)

**Code.** `schema/links.yaml`, imported by the index schema: one LinkML slot per link between base rows. The slot is the link property (`link/{source}/{table}#{column}` for a published key, `rule/…` for a link by rule); its domain and range are the base classes; annotations give the key columns, the target columns, target columns that must be empty, a separator for a cell of several keys (split there, surrounding spaces removed) and, for a link by rule, the rule. The first links are published keys within and between SDTM CT, COSMoS, SDTMIG, the SDTM Model, NCIt FLAT and the code–CUI map. A link to a Biomedical Concept goes to its row in the BC hierarchy table (one row per BC). `cfa.link` checks the links, builds each link's triples from the base graphs (a link only where the key matches exactly one target row; a key with an empty part gets none) and generates the link shapes: SHACL-SPARQL, severity Info, with SHACL-AF SPARQL targets. `checks/00_Schema` writes the link shapes. `linked/Make_Links` reads only the base graphs, writes the link graph, validates base and links against the link shapes, and renders Link_Check from the validation report. Links that start from or end at a row of a sign-in source are written to a separate file that is not published.

**Content.** The `links` named graph, Link_Check (every row with a value in a link column and no link, or fewer links than keys; broken links are reported, not repaired) and Provenance.

## Step 7 — the linked layer: links by rule (2026-11-27)

**Code.** `schema/links.yaml` gets the links by rule, each with its rule stated: SDTMIG variable to SDTM Model variable; a Dataset Specialization variable to the SDTMIG variable of its domain, else to an SDTM Model variable, else to the NSV Registry entries of its name without the domain prefix; value-list values to the terms of the bound codelist; Model Variables Qualified to the variables named, in the same class and dataset; Dataset Specialization subject and object to the variables of the same Dataset Specialization. A by-rule link IRI names its target table as well as its column, since several rules may rest on one column. New link annotations: `requires`, `unless` (a fallback applies only where earlier links found nothing), `match_empty`, `targets: all` (every matching row is linked; more targets than keys is reported), `rule_function` (the function in `cfa.link` that implements a stated rule). Link_Check gets a column `Result` (no link, or more target rows than keys), and Not resolved is joined with the link's own separator. `Make_Links` makes the links in the order of links.yaml and binds one prefix per link namespace. By-rule links that start from or end at a row of a sign-in source are written to a separate file that is not published.

**Content.** The `by-rule` named graph, Link_Check and Provenance.

## Step 8 — the COSMoS authored-model graph (2026-11-27)

**Code.** COSMoS's own LinkML model files (`model/cosmos_bc_model.yaml`, `model/cosmos_sdtm_model.yaml`) are pinned in Reference_Versions.json and read by linked as a rule document. `schema/cosmos_model.yaml` (hand-kept) states, per COSMoS class, the base table, the node rule and the base column of each slot; the column-to-slot mapping follows COSMoS's own converter, none of its value changes is taken. Class and slot IRIs are COSMoS's, as LinkML expands them. `cfa.model` checks the mapping against the model files and the base module, builds the graph, and rebuilds the base tables from it. BiomedicalConcept, DataElementConcept and SDTMVariable are base row nodes; SDTMGroup, Coding, CodeList, AssignedTerm and RelationShip are nodes by rule. A cell split at ";" gives one triple per part, so order and repeated parts are not kept; the published cell stays in base. `linked/Make_COSMoS_Model` builds the graph and runs the reverse check: the BC table and the Dataset Specialization table rebuilt from the model graph equal the base tables, split cells compared as sets of parts. README: linked also reads pinned rule documents.

**Content.** `cosmos-model.ttl`, the COSMoS export in COSMoS's authored model, every value as published; `COSMoS_Model_Check.xlsx` (the cells that repeat a part; the mapping); Provenance.

## Link_Check — Dataset Specializations that point to a retired BC (2026-11-27)

**Code.** A new link annotation, `flag` (with `flag_rule`, the rule stated): a marker the target publishes, as a column and the text the column ends with. A linked row whose target carries the marker is a result too; the link stays. It is set on the link Dataset Specialization to biomedical concept: the BC hierarchy row's `bc_short_name` ends in "[RETIRED]", the marker COSMoS publishes for a retired BC. `cfa.link` generates one more SHACL-SPARQL shape (sh:Info) per flagged link, and Link_Check gets the Result "target bc_short_name ends in [RETIRED]". The Schema sheet of Link_Check gets a column Flag.

**Content.** Link_Check gets 60 rows: the Dataset Specialization rows of 12 Dataset Specializations whose BC is one of 12 retired BCs. The link graphs are unchanged.

## Examples — the observable query starts from the test code (2026-11-27)

**Code.** `observable_concept_graph.rq` takes an SDTM CT test term (codelist code and submission value, example GLUC) instead of a bc_id. ## Examples — other tests of the BC, and a faster query (2026-11-27)

**Code.** `observable_concept_graph.rq` gets Part D: the rows of the BC's Specializations whose assigned term is in a codelist of the start terms, with only their type, the assigned term link and the BC link, the Specialization's variables link to them, and every triple of those terms and their NCIt concepts. For GLUC this adds GLUCPE and Plasma Equivalent Glucose (NCIt C163446), which the Specialization GLUCPE assigns under the BC Glucose Measurement. Each part of the query now repeats the BC-to-NCIt link of its anchor, so that an engine that evaluates the parts of a UNION separately (Oxigraph does) stays fast: under 1 second for GLUC, instead of about 30. The page shows one box per test: the test terms with the same NCIt concept share a box (for GLUC: GLUC / Glucose; GLUCPE / Plasma Equivalent Glucose), each term on click. These tests are in the Test column, with a dashed line to the BC (via the Specialization's test rows) where there is no solid line through the shared NCIt concept (7 of the 1,314 Specializations that assign a test code assign one with an NCIt code other than their BC's). For GLUC: 1,522 triples.
